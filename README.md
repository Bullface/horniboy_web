# Horniboy — Cloudflare Worker

A free-tier, install-free metasearch dashboard based on the first Horniboy commit (4fdad48b39a2e7f1dec71baf877fa436ed9091c9). Retains its compact search bar, history ribbon and site switches, with a subtle retro folk-pattern accent. No iframes, paid rendering, login, scraping of private accounts or unrestricted proxy.

## Deployment (Cloudflare Workers, recommended)
- Use this branch, cloudflare-worker.
- npm ci && npm run check
- Create a Worker from the Git repository. Build command: npm run build. Deploy command: npx wrangler deploy. Wrangler uses wrangler.jsonc and uploads dist/ as static assets, with /api/* routed to worker/index.js.
- Or deploy locally from a Cloudflare-authenticated terminal: npm run build; npx wrangler deploy.
- For an existing Cloudflare Pages Git project, select this branch, set build command npm run build and output dist. Pages Functions are included in functions/api/[[path]].js. If Pages detects the Workers-specific wrangler.jsonc, use the Workers project above instead, or remove the Workers config in a separate Pages deployment checkout. Do not deploy dist alone as a direct-upload ZIP: the API is necessary.
- Local Worker development: npm run build; npx wrangler dev. The static file alone intentionally reports the missing API.

Use the Workers Free plan. Each provider search is one inbound API request, plus bounded upstream requests. The browser searches up to four shops concurrently, progressively displays completed results, and times out both worker and client requests. Cloudflare free quotas/CPU limits can still be exceeded; no paid service is automatically provisioned. Do not expose a public high-traffic instance without access/rate controls. For private use, restrict access with Cloudflare Access if desired.

## Providers and availability
Five original providers are preconfigured; the OBI templates use the documented trailing-slash search route and BAUHAUS uses its current /suche/produkte?text= route. Store filters can be configured manually. OBI search-state extraction also understands the documented public embedded window.__INITIAL_STATE__ shape (reference: jnslmk/baumarkt-mcp, OBI adapter documentation; no browser imitation or challenge bypass). Generic extraction reads JSON-LD Product/ItemList/graph and explicitly identified public JSON products. It never executes shop JavaScript. Hornbach/Bauhaus may serve access challenges; the Worker reports blocked/unverified, not out-of-stock. It does not solve CAPTCHAs, strip headers, impersonate browsers, or replay protected APIs. Real provider compatibility must be verified from the deployed Worker; public upstreams change.

Availability comes from explicit offer fields only. OBI orderability is online, not physical store stock. Pickup is displayed only if an explicit named store and pickup offer are present. Unknown scope remains unknown. Price and stock conflicts are not guessed. Product matches use search tokens against name/brand/model/GTIN; fuzzy matches may be missed. No price history or freshness guarantee. No automatic image requests unless enabled.

## Dynamic provider list
Sites -> one line per Name | https://shop.example/search?q={search_keyword}. HTTPS, one placeholder. Up to 24. The Worker has an exact origin + path-prefix allowlist, including the initial shops and selected AT/DE equivalents. New origins/path prefixes require operator approval, using the ALLOWED_SEARCH_PREFIXES plain-text Worker variable, a JSON object, e.g. {"https://shop.example":["/search/","/api/public/products"]}. Only add public endpoints where automated access is permitted. No wildcard hosts, private IPs, credentials, arbitrary redirect targets or general-purpose proxy. The Worker checks robots.txt, uses an identifiable user agent, and does not forward cookies. Operators are responsible for provider terms. Search terms are sent to the selected providers, not stored server-side by the application; local history stays in the browser. Debug report does not include search terms or product URLs.

## Tests and troubleshooting
npm run check runs shared URL/history tests, extractor fixtures (schema.org and OBI), policy/redirect/robots tests, mock HTTP Worker tests, and parallel pool tests, then builds dist. A separate real-browser workflow uses a controlled local mock API and asserts search rendering, partial failures and diagnostics. A live public-provider smoke workflow runs once when the Worker implementation changes and can also be invoked manually (no scheduled crawling); results are technical observations, not stock validation. Tests with mock data cannot establish production access to protected sites. Use Debug and export JSON after trying your deployed site. The browser-addon branch is the alternative for websites refusing automated retrieval.
